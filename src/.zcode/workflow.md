# Workflow

本文件维护任务调查、修改和验证流程。项目入口见 `.zcode/overview.md`。

## 改动前

- Java 任务阅读 `.zcode/java-guidelines.md` 和 `.zcode/implement-warning.md`。
- GLSL 任务阅读 `.zcode/glsl-guidelines.md`。
- 阅读 `.zcode/module-map.md`，再读取命中的模块文档。
- 使用 `rg` 或显式 UTF-8 读取命令检查当前实现。

## 模块读取

- `.zcode/modules/` 不进入默认上下文。
- 必须先用 API、类名、文件名或资源 ID 缩小范围。
- 只有任务涉及模块实现、模块边界或模块文档时，才读取对应模块。

## 开发约束

- 严禁反编译任何源码。
- 严禁使用 `javap` 读取依赖库的方法签名。
- 禁止快速验证、临时方案、样例特判和无正式契约的 fallback。
- 错误设计必须从状态归属、入口语义或数据模型修正，禁止叠加补丁和过渡逻辑。
- 最终判断或编辑前，必须完整读取直接相关的入口、实现、接口、数据定义和模块文档。
- 修改必须覆盖证据证明受影响的完整正式链路；扩大范围必须有共享调用、状态或数据契约依据。
- 样例只能用于验收，禁止用样例代替正式模型。
- 行为、架构或调用链变化后，必须检查长期规范、模块边界、正式入口和项目警告。
- 文档只作入口和约束索引，运行事实以当前代码和数据为准。

## 问题处理

1. 定位证据：列出适用的文件、行号、正式入口、数据入口、状态写入点和 API；不适用项必须说明原因。
2. 读取权威：核对顶层文档、当前实现、直接调用对象、基类、接口和数据定义。
3. 证明可达：从正式入口写清触发条件、执行顺序、对象归属和状态来源。
4. 证明后果：写清可观察错误；假设风险必须标为未确认并列出缺失条件。
5. 确定范围：扫描共享入口、状态和数据，覆盖完整受影响链路。
6. 执行验证：运行项目检查，并列出需要游戏内确认的行为。

## 验证方式

- 任何已授权的文件修改完成后，必须运行完整的 `.\gradlew.bat fixProject`；命令产生的格式化改动均被视为已授权。
- 只读任务仅运行支撑结论所需的不写入检查；结论涉及项目构建状态时运行 `.\gradlew.bat verifyProject`。
- 数据、图形、音频、GLSL 或脚本行为变化后，必须列出游戏内检查。
- 验证失败时必须报告命令、退出码和阻塞原因。

## 常用命令

```powershell
# 修复全仓格式，随后编译并执行全部项目规则
.\gradlew.bat fixProject

# 不写入项目文件，检查全仓格式、编译和全部项目规则
.\gradlew.bat verifyProject

# 仅修复全仓格式
.\gradlew.bat formatProject

# 仅检查全仓格式，不写入项目文件
.\gradlew.bat verifyFormat

# 仅编译 Java
.\gradlew.bat compileJava

# 仅执行项目静态规则
.\gradlew.bat projectRulesCheck

# 构建 jar
.\gradlew.bat jar
```

## 事后要求

- 未得到用户直接要求前，禁止修改 `.zcode/` 文档。
- 长期规范、模块边界、正式入口或项目警告变化时，必须询问是否同步对应文档。
- 新增舰船、武器、插件、战术系统或代码 i18n 字符串时，必须同步 `descriptions.csv` 和 `strings.json` 中实际的文本入口。
- Java 调用链或数据列结构变化时，必须检查所有受影响的关联文件。
